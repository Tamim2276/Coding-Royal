Abstract
Clash of Codesis a multiplayer competitive programming game that adapts the high-
stakes, real-time resource management of the Clash Royale format into an algorithmic
battleground. Players match globally or challenge friends in private rooms, balancing
fast-paced code composition, multiple-choice questions, and disruptive environmental
abilities calledSpells.
This document covers the complete game design, design improvements, the two-project
architecture reference, a migration guide for the existing codebase, and the full revised
day-by-day build plan.

5 Recommended Design Improvements
5.1 Spell Cooldown
Add a30–60 second per-slot cooldownafter casting to prevent burst spell combos
(e.g., Bracket Bandit + Code Swap in rapid succession).
5.2 Active Debuff Cap
At most2 active offensive debuffson the opponent at any time. A third spell
replaces the oldest.
5.3 Disconnect Handling
A player disconnected for 60+ seconds auto-forfeits; opponent wins with a partial RP
bonus.
5.4 Spell Notifications
Every incoming spell displays a toast, e.g.:
“Opponent cast Fog of War — compiler messages hidden for 45s”

The existing project is Blazor Server. There is no need to convert it to WebAssem-

Azure Static Web Apps, which is only for WASM since it outputs purely static files).

8.4 SQLite in Both Environments
SQLite is a single file (ClashOfCodes.db). Unlike SQL Server, it requires no server process.
The connection string is simply a file path:
// In API Program.cs
builder.Services.AddDbContext<AppDbContext >(o =>
o.UseSqlite("Data Source=ClashOfCodes.db"));
For Azure deployment, copy the.db file to the App Service storage or switch to a managed
database (Azure SQL or PostgreSQL) before going to production. SQLite is perfectly fine
for development and testing throughout the 4-week build.

Using your existingRoom model (already in the database), add:POST /api/rooms
(creates a room, returns a 6-character random code),POST /api/rooms/join (finds
room by code, adds player),POST /api/rooms/start (host triggers match creation
and broadcastsMatchFound to both players). Room config stored as JSON: topic
filter, difficulty cap, Elixir mode. All endpoints require[Authorize].
Day 25 Blazor: lobby waiting room UI Both
Build a waiting room page: both players shown with avatar initials (first letter of
username in a coloured circle), a Ready toggle button, a live chat panel using SignalR
(reuse GameHub with a lobby group prefix), and the room config summary. Host sees
a Start button once both players are ready. A share button copies the room link to
the clipboard vianavigator.clipboard.writeTextthrough JS interop.
Days 26–27: UI polish
Day 26 Blazor: global visual design pass Blazor
Define a dark colour theme inwwwroot/css/app.cssusing CSS custom properties
(–color-primary, –color-surface, etc.). Add entrance animations for spell cards
(CSS @keyframes slideIn) and crown capture events. Design arena badge icons as
inline SVG. Add a pulse animation to the BE bar during Double Elixir mode. All
styling remains in the Blazor project — the API has no UI.
Day 27 Blazor: game screen layout and keyboard shortcuts Blazor
Refine the game page CSS Grid: left panel (problem statement + code editor), right
panel (opponent progress + spell hotbar). Add a collapsible problem statement
toggle. Add a Ctrl+Enter keyboard shortcut to submit code via JS interop:await
JS.InvokeVoidAsync("addSubmitShortcut", dotNetRef). Add loading spinner
components to all HttpClient calls so the UI never appears frozen during API
latency.
Days 28–30: Testing and deployment
Day 28 End-to-end testing with two accounts Both
Open two browsers (Chrome and Firefox). Register two separate accounts. Play a
full ranked match from queue through to result: verify crown capture, spell effects
on both sides, BE deduction, RP update, and arena promotion. Log every bug as
a GitHub issue. Verify JWT expiry is handled gracefully (redirect to login, not a
crash or blank screen).

Day 29 Bug fixes and error handling Both
Fix all bugs logged on Day 28. In Blazor, add<ErrorBoundary> wrappers to the
game page components. Wrap allHttpClient calls intry/catch with user-friendly
error messages. Handle 401 responses by clearing the stored JWT and redirecting to
the login page. Handle Judge0 API timeouts in the API by returning a structured
error response rather than a 500 crash.
Day 30 Deploy both projects to Azure Both
DeployClashOfCodes.APIto Azure App Service (Free or Basic tier). Deploy
ClashOfCodes(Blazor Server) to a second Azure App Service — Blazor Server re-
quiresaserverprocess; itcannotuseAzureStaticWebApps. UpdatetheAPI’sCORS
WithOrigins to the live Blazor App Service URL. Update the BlazorHttpClient
base address to the live API URL (use environment-specificappsettings.json).
Store all secrets as Azure environment variables: SQLite path, JWT secret key,
Judge0 API key. Never commit secrets to source code.

A Key Commands Reference
# Create the API project and add to solution
dotnet new webapi -o ClashOfCodes.API
dotnet sln add ClashOfCodes.API/ClashOfCodes.API.csproj
# EF Core packages for the API
dotnet add package Microsoft.EntityFrameworkCore.Sqlite
dotnet add package Microsoft.EntityFrameworkCore.Tools
dotnet add package
Microsoft.AspNetCore.Identity.EntityFrameworkCore
# JWT authentication (API)
dotnet add package
Microsoft.AspNetCore.Authentication.JwtBearer
# SignalR (API)
dotnet add package Microsoft.AspNetCore.SignalR
# SignalR client (Blazor)
dotnet add package Microsoft.AspNetCore.SignalR.Client
# EF Core migrations (run from ClashOfCodes.API folder)
dotnet ef migrations add AddIdentity
dotnet ef database update
# Run both projects simultaneously (two terminals)
cd ClashOfCodes.API && dotnet run # Terminal 1
cd ClashOfCodes && dotnet run # Terminal 2
# Publish API for Azure
dotnet publish ClashOfCodes.API -c Release -o ./api-publish
# Publish Blazor for Azure
dotnet publish ClashOfCodes -c Release -o ./blazor-publish
